# Changelog

All notable changes to this package are documented here.

## Unreleased

## 0.8.0

- **New opt-in replacement of Swarm-managed artifacts: `--allow-replace [selector]` (repeatable) and `ServerOptions.allowReplace`.** Off by default. A bare flag (or `true`) lets an upload replace any managed artifact that holds its name; a selector (or each entry of an iterable) names one exact artifact name or one release template in the grammar of `artifactPatterns`, matched against the final basename: `beta-{version}`, `latest.json`, a bare `{version}` (the names that are SemVer versions, not every name), `{series}-nightly`. A `/` (a source parent is client-asserted and not stored) is refused, every value is validated even beside a bare flag, `history-` names, duplicates, more than 64 selectors and non-strings throw `PROTOCOL_INVALID` with a fixed message that echoes nothing, and a selector that is 64 lowercase hexadecimal characters is still refused by the CLI's secret guard. `server.allowReplace` is `false`, `true` or a frozen copy.
- **Only managed artifacts, even with every name allowed.** Replacement needs a managed artifact of the same kind whose content still matches its record. An unmanaged file or directory, a managed directory with a child added, changed or removed (an empty directory included), a symlink, and a file where a directory is (or the reverse) are left exactly as they are and the upload gets `FILE_EXISTS`. The replaced artifact stays as `history-<its transfer id>`.
- **Allowing replacement pins nothing.** Retention is unchanged: `--allow-replace` never pins an artifact against age, count, version, quota or scoped retention. Only the legacy `--replace-name` / `replaceNames` keeps its standing pin on the current artifact. The artifact being replaced is held only for the commit's own pre-commit pass (a temporary pin under the root lease), and an unfinished replacement's journal protects what it owns from retention and from the scrub until recovery finishes.
- **`--replace-name` / `replaceNames` now also replace a managed directory** (before, a directory was create-only and such an offer was `FILE_EXISTS`). File behavior is unchanged.
- **Directories are replaced by an atomic exchange with a durable, recoverable transaction.** The new tree is parked at a private path, one exchange puts it at the public name and the old tree at the private path, and the old tree then becomes `history-<id>`: the public path is never missing and never half published, a continuous reader never sees either, and the old tree is never deleted. The journal (version 4) names every path with the inode identity it must hold, and recovery decides from what it observes: a durable new current record means the replacement is completed, otherwise it is undone exactly (the exchange repeated, the new tree back in staging, the session resumable); an unexpected inode, kind, symlink or occupant stops recovery without touching it. When the returning content already has a history copy (A, B, A) that copy is parked privately, with its record, and restored exactly if the replacement does not complete; it is removed only after the new current record is durable. Every move is preceded by a proof of the inode and of the free destination. New `StorageAdapter.atomicSwap(first, second)` (optional; an adapter must exchange atomically or change nothing, never emulate). The default adapter provides it on Linux and macOS through the new dependency `fs-native-extensions` (Holepunch), **loaded only when a directory is actually replaced**: importing the package, a `Client`, or running a server that never replaces a directory does not load the native addon. Windows has no atomic exchange. A storage without it, or a filesystem that refuses it (tested once per layout on scratch directories in the private state), refuses the replacement with `UNSUPPORTED_STORAGE` before anything published changes. File replacement needs none of this.
- **A busy artifact is retried, not replaced.** While an awaited upload hook or an explicit link request (under `rollback` or `keep`) is using an artifact's public path, and while a queued or running detached hook or an open link rollback journal names it, replacing that name (a file or a directory, `--replace-name` included) is refused with the retryable `FILE_BUSY`, at admission and again under the root lease before anything changes. A hook that already failed, or a request that settled, holds nothing. An automatic link's `afterLink` runs again for the replacement (`LINKED`); an explicit `link` request for the same target runs it (`UNCHANGED`) for the bytes that are there now.
- **An interrupted A, B, A on a file no longer loses the returning content's history.** Through 0.7 a file replacement that returned content already held as history (A, B, then A again) deleted that history file and its record before the new current record was durable, so a crash or abort in between left neither. The history file and its record now stay exactly as they were until the new current record replaces the history record in one atomic step, and the superseded duplicate file is removed only afterwards, once proven to be a copy of the returning content (by inode within the attempt, by bytes from a journal alone); an abort or a failed or ambiguous write puts the history record back. The returning copy is looked for after the commit's own retention pass, so a pass that legitimately evicts it (quota, age, count) leaves an ordinary replacement instead of failing the commit. No persisted format changed (the version 2 journal and the records are the same), so this adds no state barrier, and a journal an earlier release left, after it had already removed the duplicate, still recovers. But the history record now stays where it was until the new current record is durable, and **0.7.x refuses to start on a pending version 2 journal of such an interrupted replacement** (`Commit sidecar does not match journal`, before it changes anything); it does not recover it. Start 0.8 once to recover, stop it cleanly, and only then roll back to 0.7.x; see the rollback note in `docs/operations.md`. A 0.7.x that meets the journal after the new current record became durable completes it and may leave the superseded duplicate file, which only blocks a later replacement of that history name with `FILE_EXISTS`. Full behavioral parity with 0.7.x on this journal is not claimed.
- **Downgrade barrier: the first directory replacement makes older releases refuse the state directory.** Releases through 0.7 would quarantine a version 4 journal as corrupt and delete a version 4 record as invalid, and they read only the string `root` of the state directory's record. So before any version 4 journal, record or deduplication step, the state directory's record `.swarm-deploy-state.json` is durably rewritten (a synced private file renamed over the old one, then the directory synced) to `{ "version": 2, "root": { "path": "<root>", "requires": ["directory-replacement-v1"] } }`; an older reader sees a `root` that is not a string and refuses to start, before it reads a journal, a record or a session. This release reads both shapes (and `reset-storage` keeps the record), and refuses a record that requires a feature it does not know. Nothing writes the strict form unless a directory replacement actually begins, and nothing ever removes it. **Once a directory has been replaced, keep this release or restore a backup of the state directory taken before.**
- **Client `idleTimeout` is 10 minutes by default and configurable up to 2147483647 ms** (`ClientOptions.idleTimeout`, `swarm-deploy upload|link --idle-timeout`). It was 60 seconds and could not exceed 5 minutes. Any invalid value (zero, negative, fractional, above 2147483647) is rejected, never shortened. It bounds one wait, not a transfer: each protocol read, each backpressured write, and the single wait for the final answer (which covers verification, commit and awaited hooks, a directory replacement included) restart with every chunk that moves. The connect timeout is unchanged (30 seconds, at most 5 minutes), and so is the server's own `idleTimeout`. `MAX_IDLE_TIMEOUT` is exported from the client module.
- **Bare: the no-follow and exclusive-create flags are right on every supported platform and architecture.** Bare's `fs` provides neither `O_NOFOLLOW` nor `O_EXCL`, so every safe open of a regular file (private state, journals, staging, published files, upload sources, and the CLI's seed file reads and `keygen` writes) used fallback numbers, and two were wrong. On Linux ARM (arm64, arm) the x86 `O_NOFOLLOW` value (0x20000) is `O_LARGEFILE`, so a symlink at the final path was followed; on macOS the Linux `O_EXCL` value (0x80) is `O_FSYNC`, so a private-state exclusive create opened an existing file instead of refusing it. 0.7.0 carries the same fallbacks. They now come from one table shared by the storage guards and the CLI, keyed by platform and architecture (Darwin: `O_NOFOLLOW` 0x100, `O_CREAT` 0x200, `O_EXCL` 0x800; Linux: `O_NOFOLLOW` 0x20000 on x64 and ia32 and 0x8000 on arm64 and arm, `O_CREAT` 0x40, `O_EXCL` 0x80). The runtime's own constants still win where it has them, a provided value that is not a positive integer is ignored, and any other platform or architecture refuses to open with the same error as before instead of guessing. Node is unaffected (its constants are complete), and no option, API or persisted format changed.
- **Wire protocol and persisted formats.** No wire field or version changes: a 0.6.3 (or earlier) client uploads, and replaces, against a 0.8.0 server that allows it. New persisted forms are the version 4 history directory record, the version 4 journal, and the strict state record above; none is written unless a directory is replaced.

## 0.7.0

- **The free-disk reserve no longer counts bytes twice.** Admission compared the free space with the reserve plus the full reservation (TAR plus extracted payload) of every open session plus the new upload, so a session whose TAR bytes were already on disk was counted both in the free space and in its reservation. It now adds up only what open sessions can still write: a receiving session's remaining durable TAR plus its full payload (the payload stays owed through extraction), and nothing for a verified or deleting session. `reservedBytes`, `maxStagingBytes`, the 1 GiB default, the staging cap, restart behavior, and the retention of the TAR until commit are unchanged. **This does not reduce the peak of a fresh upload**, which still needs its TAR and its extracted payload at once, and it does not free any space.
- **New opt-in scoped retention (`ServerOptions.retentionScopes`, repeatable `--retention-scope`).** A scope such as `{ pattern: 'beta-{version}', maxCount: 5, maxAge: 604800000 }` (CLI `'{"pattern":"beta-{version}","maxCount":5,"maxAgeDays":7}'`) removes old committed artifacts whose basename matches the template, whether or not `artifactPatterns` admitted them, so a server with no artifact patterns can still bound one family of names. `maxCount` uses the existing newest-N keep set over every match, pinned ones included; `maxCount` and `maxAge` combine (an artifact over either is removed) and several scopes are unioned. Nothing a link, rollback journal, replace-name, or detached hook pins is ever removed, replacement history copies are never matched, and artifacts that match no scope and files nobody uploaded are untouched. A pattern needs at least one literal character (no bare `{version}`) and has no path; a `maxCount` needs `{version}` in it (a template without it makes every name its own series, so the count could never remove anything and is refused, while an age-only scope may use `{series}`). At most 16 scopes are accepted, and the list is validated and copied at construction (`server.retentionScopes`; `RetentionScope` is exported). The `retention` event gains `scopedDeleted` only when scopes are configured. Off by default: without scopes, retention behaves and reports exactly as in 0.6.3. The first pass after a restart removes every unpinned artifact a scope selects and there is no dry run. See [Scoped retention](https://github.com/tetherto/swarm-deploy/blob/main/docs/artifact-patterns.md#scoped-retention).
- **CLI: `--resume-ttl <ms>`, `--cleanup-interval <ms>`, `--min-free-bytes <bytes>`.** Each is a positive integer (`--cleanup-interval` at most 2147483647) forwarded to the server only when given; defaults stay 7 days, 15 minutes, and 1 GiB. **`--resume-ttl` and `--cleanup-interval` change what the server actually removes.** Once the server restarts with a new value, the startup pass (and then every scheduled pass and admission) removes each session whose last activity is older than the TTL, with its staged bytes, so a shorter `--resume-ttl` can discard the progress of an interrupted upload (the client then starts it over) and reclaims that staging space; a shorter `--cleanup-interval` makes scheduled passes, which also expire sessions and apply retention, run sooner. A session with a live transfer, one being verified at that moment, and one being deleted are never expired; an idle session that already finished verification is eligible. `--min-free-bytes` only changes the reserve admission must leave: it frees no data and starts no cleanup, and the CLI has no way to turn the reserve off. The API keeps `minFreeBytes: 0`.

## 0.6.3

- **Failures now reach the client with the server's own reason.** Through 0.6.2 the server destroyed the connection right behind every failure answer except `HOOK_FAILED`, so a client could see only `connection reset by peer` for an ordinary failure such as `DISK_RESERVE` or a failure while receiving. Now every terminal failure answer that was written (admission `REJECTED`, `FAILED` final, `FAILED` link result) is followed by ending the stream and a bounded 5-second grace, as `HOOK_FAILED` already was; a rejected offer's connection is no longer left open for the peer to close. The lingering connection holds only its connection slot, for at most that long. An answer that could not be written, an unauthorized or over-capacity peer, and a closing server still destroy the connection at once. No wire field, version, authentication, resume, checksum, publication, retention, or hook behavior changes. This does not create disk space or change any limit; it only reports them.
- **Unwrapped raw upload errors are no longer reported as `PROTOCOL_INVALID`.** Through 0.6.2 any raw (non-`SwarmDeployError`) error in an upload was reported as `PROTOCOL_INVALID`, so a server fault could look like an invalid request. Now an explicit `SwarmDeployError` always keeps its stable code: a malformed record or mismatched transfer ID stays `PROTOCOL_INVALID`, as does a peer's own stream failing, and so does a failure that the storage layer wraps in its own `PROTOCOL_INVALID` guard (for example opening or checking a staging file or directory, rolling back a failed append, or legacy state in the output root), even when a known errno lies under it. Only a raw error that reaches the server unwrapped is classified: a known errno maps to an existing code (`ENOSPC`/`EDQUOT` to `DISK_RESERVE`; `EXDEV`/`ENOSYS`/`ENOTSUP` to `UNSUPPORTED_STORAGE`; `EACCES`/`EPERM`/`EROFS`/`EIO` to `COMMIT_FAILED`, whose explanation is now "could not write or commit"), and anything else is the one new stable code `SERVER_ERROR` with a fixed explanation (`ERRORS.SERVER_ERROR`). The fixed explanation of `PROTOCOL_INVALID` now says it can be a protocol or a storage-state check failure, so it no longer implies that the request or the client version was at fault; the server log's `phase` and `systemCode` say more. Link requests are unchanged (an unclassified failure is `LINK_FAILED`). No record field or version changes and the answer still carries only the code. **A client older than 0.6.3 does not know `SERVER_ERROR` and fails closed**: it rejects that answer as an invalid record and cannot show the code, so read the server log for it; requests that succeed are unaffected, and the mapped codes already existed. `Direct upload failed` and `Direct link failed` now also log the `phase` and, from a short fixed list, the errno name as `systemCode`, never an error message, path, stack, or hook text. `Client` still reports a local raw exception as before.
- **A client reads a failure answer sent while it is still sending.** A server that fails an upload while receiving now reaches the client as that code even under backpressure: the client keeps reading while it sends, stops sending when the server answers, and reports the answer. Local failures (changed source, an abort) and answers that are unexpected or unreadable (including a completion before the payload is in) are never replaced or taken for success, and the wait for an answer after a failed send is bounded.
- **Errors say where they came from.** `Client` errors carry `remote` (the server's own answer), `transport` (the connection failed or closed with no reason), `operation`, and `phase` (`connect`, `request`, `admission`, `streaming`, `final`), set on the error that was thrown, so types, codes, causes, abort and timeout distinctions are unchanged. Decide on `remote` and `transport`: a local failure (a changed source, an unreadable answer) has neither but may still carry `operation` and `phase`, and an abort carries none of the four. A server answer's message now names the code and a fixed explanation (`Server rejected upload (FILE_EXISTS): ...`), never server text. `RequestOperation` and `RequestPhase` are exported.
- **CLI.** `upload` prints that message, or for a connection that gave no reason says where it failed and that no reason was received (and that the server-side outcome is unknown), never the stream's own text as a reason; `link` still prints only its stable code for server answers. With `--json`, a failed `upload` or `link` now always prints one object, `{ "code", "origin"?, "phase"?, "hookResult"? }` (`link` adds `target` and `name` first), where it printed nothing unless the server returned `onFailure` data: **scripts that treated empty stdout as the failure signal must use the exit status, which stays `1`.** Nothing from a message, cause, or stack is printed; usage and configuration errors still exit `2` with no JSON. See [Failure output](https://github.com/tetherto/swarm-deploy/blob/main/docs/cli.md#failure-output) and [Troubleshooting failed uploads](https://github.com/tetherto/swarm-deploy/blob/main/docs/operations.md#troubleshooting-failed-uploads).
- **Limits.** A client key the server does not allow, an over-capacity server, a crash, and a network failure still end the connection with no answer; they are reported as unexplained transport failures, not as a server reason. A server older than 0.6.3 still resets the connection behind most failure answers whatever the client version, so upgrade servers first.
- **Quieter logs.** The retention scan no longer repeats `Ignoring unknown committed path` for every unmanaged entry on every pass: a name is logged when it first appears (and again if it went away and returned), at most 32 per scan, with the rest counted once in `Ignoring more unknown committed paths`. Invalid managed state and failed scans or operations are still logged every time; unmanaged files are still never adopted or deleted.

## 0.6.2

- **New `ServerHooks.beforeClose(): void | Promise<void>`, exported by hooks modules as `beforeClose` (minimum 0.6.2).** A general teardown callback so a hook that changes something outside the server can cancel and fully drain that work before the server lets go of its storage. Before, closing aborted the waits on operation hooks and abandoned a callback that was still running, so a publisher could keep mutating an external store after the server had rolled back locally, released the storage lock, and let another server start. It is not an operation hook: it takes no `--hook-mode` or `hookModes` entry (refused as an unknown key), is always awaited, and changes no wire record or the point at which ordinary post-hooks respond. There is no Snap-specific code in the package.
- Ordering of `close()`: admission stops, `beforeClose` is called synchronously in that same call (so it can cancel external work before anything else proceeds), the artifacts of the queued and running detached calls are noted, the server's own operations are aborted as before (which ends every detached call at once, each releasing its own pin), scheduled retention is stopped (its interval cleared, a pass already running waited for) before the wait on the hook, and the server closes its stores, releases the storage lock and emits `close` only after `beforeClose` and the operations finished. The noted artifacts stay pinned for retention until that stop has completed, so a pass that starts, or is already running, while the transport is still closing cannot delete what a cancelled callback is still using; after it no pass can run, so none does while the hook drains. The notes cover detached calls only; managed-link and rollback-journal pins are persistent and unaffected. Every `close()` returns one promise and the hook runs once, even when `close()` is called again, concurrently, or from inside the hook (which must not wait for the server's own `close()`). It runs for any close, and for a failed `listen()` only if that start had already begun accepting connections.
- **The hook owns its own bounds.** The server adds no timeout and never abandons it: a `beforeClose` that never settles keeps `close()` pending (and the CLI from exiting) and the root locked. Hooks without `beforeClose` keep the existing bounded close even if an operation hook never settles; nothing else waits on hook promises. If it throws or rejects, `close()` rejects with `HOOK_FAILED` (fixed message, raw error only as `cause`, log carries only the code), the `close` event reports `failed`, and the server still tears down its own resources, the lock included; the CLI exits `1` with `Cleanup failed`.
- An older server ignores a `beforeClose` module export without error and refuses it in `ServerOptions.hooks`, so a module that depends on it must require 0.6.2 or newer. See [Shutdown cleanup: beforeClose](https://github.com/tetherto/swarm-deploy/blob/main/docs/hooks.md#shutdown-cleanup-beforeclose). The 0.6.1 private-state fix is unchanged.

## 0.6.1

- **Security fix: private state no longer lives in the served output root.** Through 0.6.0 all internal state sat in `<storage>/.swarm-deploy`, so a web server serving the storage root exposed it. That state holds session and commit metadata (uploader public keys, digests, optional source-parent paths), lock records (a process ID and a random token), managed-link ownership and rollback records, and incomplete partial artifact payloads. It holds no seeds by default. The output root now contains only published artifacts and managed public links: no staging, sessions, commit or link records, journals, publications, trash, locks, or reset archives, at any depth.
- Default state is `~/.swarm-deploy/<id>` under the home directory of the user running the server (resolved with the runtime's `homedir`, never the working directory). `<id>` is derived from the real path of `--storage`, so each output root has separate state, the same state is found after a restart or through a path alias, and an alias cannot create duplicate state. New `--state-dir <absolute-dir>` for `server` and `reset-storage`, and `ServerOptions.stateDir` (also readable as `Server.stateDir`), choose another location. `reset-storage` resolves the location exactly as the server does and prints a `state:` line, which, with the paths named in its errors, is how to find the directory; the server does not log it. The home directory is the one the runtime reports (`os.homedir()`, which honors a `HOME` set by the service manager). The layout helpers stay internal.
- The state directory must be outside the output root (not the root, inside it, above it, or reachable through a symlink alias) and on the same filesystem, because publication, link replacement, tree rename, retention trash, and recovery rely on atomic renames and hard links between the two. A state directory on another filesystem fails before anything is staged or published, with an error that names `--state-dir`; there is no copy fallback and no visible temporary fallback. On Linux the two must also be on one mount: `rename` and `link` fail with `EXDEV` between two mount points of one filesystem (bind mounts, container volumes), so startup compares mount IDs from `/proc/self/mountinfo` (no dependency). That file is read as bytes, through at most 4 MiB plus one byte, and a larger table is not used; the size is never taken from `stat`, which is zero for such files. Where the table is unavailable (it cannot be opened or read, or it exceeds the cap) only the device check runs, and a publication refused with `EXDEV` is logged once with the way out. Other platforms keep the device check. When the output root is itself a mount point (a volume mounted at `--storage`), no directory outside it can share its mount, so both the cross-device and the cross-mount errors say to mount a common parent and use one subdirectory for `--storage` and another for `--state-dir`. The adapter wrapper that reports `EXDEV` calls every method and getter of a custom `ServerOptions.storage` adapter with the adapter itself as `this`, so class adapters with `#private` fields keep working. A path whose device or inode number JavaScript cannot represent (some macOS system volumes) no longer hides this error as an identity failure; only the output root's own identity must be exact. The state directory is created and kept at mode `0700` and its final directory cannot be a symlink. A directory that is refused for holding other files, another root's record, or a nested legacy directory is checked read-only first and keeps its permissions.
- The directory records the output root it serves (`.swarm-deploy-state.json`), so a custom location is never silently reused for a different root. The record is written to a private name, synced, and published with a no-clobber hard link, then the directory is synced and the record read back, so two initializers racing for one directory cannot replace each other and a crash cannot leave a torn record; abandoned temporaries older than ten minutes are swept.
- **Upgrade: stop the server first.** A root that still holds `<storage>/.swarm-deploy` makes `server` and `reset-storage` refuse to run, and print the offline migration and rollback commands for your state location. Every path in them is a single-quoted POSIX shell literal, and the migration command refuses to run when the destination exists or is a dangling symlink, so it can never nest the legacy directory inside it; if the destination exists the error says so and how to choose another. A legacy directory that was nested that way earlier is refused, not ignored. Nothing is read, moved, or deleted automatically. Moving the stopped server's directory keeps its ownership and recovery data intact; start the server once with `--initialize-state` to bind it. Deleting it instead starts fresh state, which also needs `--initialize-state` while the root holds published files: uploads in progress start over, existing artifacts become unmanaged (their names stay occupied until removed, and they are never adopted or deleted), and managed links lose their ownership records. See [Private state](https://github.com/tetherto/swarm-deploy/blob/main/README.md#private-state).
- **New `--initialize-state` flag and `ServerOptions.initializeState`.** The storage lock now lives in the state directory, so an instance run with different state settings (another `--state-dir`, user, or `HOME`) would have started its own state and run beside the first, where 0.6.0's lock in the root excluded it. Starting new or unbound state, or binding a directory that holds entries but no record of its root, is therefore refused while the output root holds entries, or the directory itself holds entries, unless this one-time acknowledgement is given; leave it out of normal startup. State that is already bound needs no flag. An explicit `--state-dir` is also refused when the same user's default location for the root can be read and already holds state bound to it; a default location the process cannot examine (a hardened service that cannot enter its home directory) is not a conflict, so an explicit `--state-dir` keeps working there. If `<storage>/.swarm-deploy` reappears while the server runs, new uploads and link requests and retention passes are refused; one error is logged when it is first seen, each refused scheduled retention pass logs its own failure, and a refused link request still gets its `LINK_FAILED` answer (the connection is closed after it, as after a failed hook, rather than reset). Run every server and `reset-storage` for one root as the same user with the same `HOME` and state settings. Two instances starting at the same moment on an empty root with different settings are not detected, and nothing here promises exclusivity across users or releases. Back up and restore the output root together with its state directory.
- Documentation and `SECURITY.md` describe what the state holds, that it must never be served, and the migration. Releases through 0.6.0 may have exposed that state wherever the output root was served; nothing here inspects or deletes old copies.

## 0.6.0

- **Behavior change: post-operation hooks are detached by default.** `afterCommit`, `afterLink` and `onFailure` are now `detached` unless the operator declares them `response`: a detached hook runs after the answer was written, nothing waits for it, its return value is never read, and its failure is logged (`Detached hook failed`) and can never change an answer already sent or call `onFailure`. Until 0.5.x every one of them was awaited and a failure failed the upload or the link request. **Deployments whose publishing or deployment step must succeed for the operation to succeed must mark that hook `response`** (the `examples/link-publisher` module now does); `beforeCommit` is a validation gate and stays awaited. See [Response and detached hooks](https://github.com/tetherto/swarm-deploy/blob/main/docs/hooks.md#response-and-detached-hooks) and [Migrating to 0.6.0](https://github.com/tetherto/swarm-deploy/blob/main/docs/hooks.md#migrating-to-060).
- Declare it explicitly, never inferred from the callback (no `async` or return-value introspection): `ServerOptions.hookModes` (`HookModes`, `HookResponse = 'response' | 'detached'`, validated and frozen, only for configured `afterCommit`/`afterLink`/`onFailure`), a named or default `hookModes` export of a hooks module, and the repeatable `swarm-deploy server --hooks <module> --hook-mode <afterCommit|afterLink|onFailure>=<response|detached>`, which overrides the module per hook. `loadHooksModule` now returns `{ hooks, modes }` (it is internal).
- A `response` hook may finish with `undefined` or return a plain JSON object (`afterCommit`, `afterLink` and `onFailure` may now all return `HookResult`); the value is read and checked on every call whatever the client asked, so an unusable one fails the call as `HOOK_FAILED` (for 0.5.x hooks that returned something unrelated, return `undefined`). What the client asks for (`hookResult: true`, `--json`) only decides whether the checked data is sent back, never whether the server waits.
- Hooks see how the operation ended: every post-operation context has `outcome` (`OperationOutcome`): `succeeded` for a `response` hook, which runs while the operation is still succeeding; a `detached` `afterCommit`/`afterLink` starts after the answer and sees `succeeded` or `{ status: 'failed', code, phase }` when a later awaited step failed an upload whose artifact was already committed; `onFailure` always sees the failed outcome with the stable code the answer reports. A response hook's success can never turn a failed operation into a success.
- `onFailure` is now the failed-operation hook for both operations, including failures before any durable artifact or link exists (no path is made up: `path` is `null`). It runs for every failed upload connection whose offer was decoded and every failed link request (new `HookFailureContext.operation`, `request`, `outcome`, and phase `link`), and `HookFailureContext.artifact` is `null` for a link request that failed before its target was resolved. Declared `response`, it is awaited before the failed answer and may add data to it; its own failure, an unusable value, or a closing server leaves the primary failure's code unchanged, is logged, and never calls it again.
- Detached execution is best effort and process-local: it starts outside every lease, upload slot and transfer guard; per link name (decision order) and per artifact name it runs one call at a time; at most 1024 calls are queued or running (extra ones are dropped and logged); the artifact of a queued or running call is pinned against retention; closing the server drops queued calls and abandons a running one without waiting for hook code. There is no persistent queue, no retry and no exactly-once promise.
- Return data for uploads: `Client.upload(path, { hookResult: true })` and `swarm-deploy upload --json` ask for it; `UploadResult.hookResult` is `{ afterCommit?, afterLink?: [{ name, target, result }] }` (the combined JSON is bounded to the same 3 KiB, and parts that are valid but too large together fail the upload as `HOOK_FAILED`), and a failed request's error carries `error.hookResult` (`{ onFailure }` for an upload) next to its unchanged primary code. On the wire this is one new optional offer key and one optional answer key (`CONTROL_VERSION` is still `1`): it is sent only when asked for, is not part of the transfer identity, and an older strict server rejects an opted-in offer, so upgrade servers before clients that ask. Requests that do not ask are unchanged.
- Failure data is safe by construction: an upload's `{ onFailure }` value is bounded together with its wrapper before any answer is written (so data that fits alone but not wrapped is dropped and logged, never replacing the primary code), a detached `onFailure` is scheduled even when the rejection could not be written and pins the durable artifact its failure concerns (from the commit record, nothing for an early failure), and the wire tightly separates success keys (`afterCommit`, `afterLink`) from failure keys (`onFailure`) and refuses empty receipts and empty `afterLink` lists.
- Explicit link rollback and `hookFailure` apply to a `response` `afterLink` only. A detached `afterLink` cannot fail the request, so the request writes no rollback journal, restores nothing, and its decision is final; an upload's automatic links and artifact bytes stay committed either way.
- **Behavior change.** A failed `response` `afterLink` on an explicit link request (`Client.link`, `swarm-deploy link`) now restores the previous local symlink and its ownership record before the request is answered `HOOK_FAILED`, or removes a link the request created. Until 0.5.x the new link stayed. The request still waits for the hook in both modes and a failure is still `HOOK_FAILED`; nothing the hook did elsewhere and no uploaded artifact is undone, and an upload's automatic links are unchanged. After a rollback the same request links afresh and returns `LINKED`; a request that changed nothing still returns `UNCHANGED`.
- Add the opt-out: `ClientLinkOptions.hookFailure: 'rollback' | 'keep'` (default `'rollback'`, exported as `ClientLinkHookFailure`) and `swarm-deploy link --hook-failure <rollback|keep>`. `keep` leaves the new link in place, as 0.5.x did. The policy is independent of `hookResult` and `--json`. The server link event carries `rolledBack: true` (and no `result`) only when a failed request was restored; `ServerLinkEvent.rolledBack` is the new optional field.
- **Upgrade servers before clients.** A current client always sends the policy as a new optional field on the existing link request (`CONTROL_VERSION` is still `1`, the answer is unchanged), so a server older than 0.6.0 rejects the request and the call fails instead of silently keeping a link the caller expects to be rolled back. A 0.6.0 server treats a request without the field, from an older client or CLI, as `rollback`, so for them the default changed; pass `keep` where automation relied on the link surviving a failed hook.
- What is restored, and when it refuses: the previous visible state (no link, or an adopted symlink's exact text, which is only stored and written back and never followed) and the previous ownership record, including a record-only change such as a refreshed transfer ID. The restore is compare-and-restore: a link or record that is neither the previous state nor the one the request made (a regular file, another symlink, a replaced link, an edited or removed record) is never overwritten, the request fails with `LINK_FAILED` instead, and the journal stays so that name fails closed until an operator resolves it. A request only ever acts on a journal that is still its own (same token and recorded states): a missing, replaced, or edited one fails closed with `LINK_FAILED` and is never erased by the request that lost it. If creating the link itself fails, the failure is not taken to mean no link was made: the journal's restore looks at what is there, removes a link the request made, puts the record it replaced back instead of deleting it, and removes the journal, but only while the journal, link, and record are still the request's own; anything else is left untouched and the journal stays. An entry that was already at the name (`EEXIST`) is never removed or adopted, and the request is a `LINK_CONFLICT`. A previous symlink whose text cannot be restored byte for byte (empty, over 4096 bytes, containing NUL or the replacement character) is refused with `LINK_CONFLICT` before anything changes in rollback mode; `keep` still adopts it.
- A request that changes a link writes a small durable journal, `.swarm-deploy/links/<sha256(link-name)>.rollback.json` (at most 32 KiB, validated strictly), before it changes anything, and removes it once the hook has succeeded or the change was restored; an idle server has none. Removing it after a successful hook is final: refreshing the server's managed-name list comes after it, and a failure there is only logged and changes neither the answer nor the link. After a crash the next start restores the previous link and record before retention runs or a client connects. A journal whose state changed in the meantime is left alone: that name is blocked, its artifacts stay pinned, and the rest of the server starts. A corrupt journal stops the server from starting. While a journal exists, retention keeps both the attempted and the previous artifact, including the artifact a previous adopted symlink names when its text, compared only as a string and never resolved, is exactly the artifact's name, `./name`, or `<storage root>/name`, each optionally followed by one `/`. See [Rollback and its limits](https://github.com/tetherto/swarm-deploy/blob/main/docs/hooks.md#rollback-and-its-limits).
- Explicit link requests for one name now run one at a time, in arrival order, from the decision through the hook to the finalize or restore, in both modes, so a request never decides against another's unfinished change; the storage-root lease is still never held across hook code, and other links, uploads, and retention are not delayed. A queued request does not change the link until the one ahead has finished (previously it repointed the link immediately and only its hook waited).

## 0.5.0

- Add an opt-in way to get data back from `afterLink` for an explicit link request. `afterLink` may now return a plain JSON object (or nothing, as before), exported as the `HookResult` and `HookResultValue` types. `Client.link(target, name, options?)` takes `ClientLinkOptions { hookResult?: boolean }`, and with `hookResult: true` the resolved `ClientLinkResult` carries `hookResult` when the hook returned an object. `swarm-deploy link --json` is the CLI form: it prints one JSON object `{ target, name, status, hookResult? }` instead of the text line. What is returned is chosen by the hook author; nothing is taken from the context, errors, paths, or the environment. Use it to report, for example, an accepted external submission's ID or evidence URL. It is data transport, not proof of publication; see [Link publication hooks](https://github.com/tetherto/swarm-deploy/blob/main/docs/hooks.md#link-publication-hooks).
- Nothing changes for callers that do not ask. The default request and answer keep their exact bytes, an older client or CLI needs no change, and an upload's automatic links and a request without the option ignore the return value without reading it, even when it is not valid. `afterLink` is still awaited before `LINKED`, `UNCHANGED`, or `HOOK_FAILED` is sent, and the per-link order, root-lease release, abort behavior, and the retry that reports `UNCHANGED` are unchanged (the retry runs the hook again and returns that run's result).
- The wire change is one optional field on the existing link records (`hookResult: true` on the request, `hookResult` on a `LINKED` or `UNCHANGED` answer); `CONTROL_VERSION` is still `1`. The decoders reject any other shape, a result nobody asked for, and a malformed one. A server older than 0.5.0 decodes link requests with an exact key set and rejects the opted-in request, so an opted-in client fails instead of returning without the data: upgrade servers before clients that ask.
- A returned value must be a plain JSON object of strings, finite numbers, booleans, `null`, arrays, and plain objects, at most 8 levels deep and 3072 UTF-8 bytes of compact JSON (the 4 KiB control record limit is unchanged). When the caller asked, a value that is not valid (`undefined`, a function, a symbol, a BigInt, `NaN`, a class instance such as `Date`, a `toJSON` method, a getter, a cycle, too deep, too large, or not an object) fails the request as the stable, sanitized `HOOK_FAILED`, leaves the durable link in place, and can be retried safely; `onFailure` receives an error that names the reason and the path inside the result but never a value. The result is not written to events or logs.
- Documentation: the three levels a result can describe are the link status, what the hook reports (such as an external submission), and the final published status. The last happens outside the call, and a store review can outlast the client's idle timeout (5 minutes at most), so the hook should return a submission's acceptance rather than wait for publication. The server keeps no queue or job store, and this release adds no store clients or dependencies.

## 0.4.2

- An explicit manual link request (`Client.link`, `swarm-deploy link`) now takes over an existing symlink at the requested name that has no ownership record, such as one made by hand before the storage root was managed. After the target and name pass every existing check, the symlink itself is replaced atomically by the requested link and a manual ownership record is written; the first request returns `LINKED` (even if the old link already read as the target) and repeats return `UNCHANGED`. The old link is never followed, so whatever it pointed at (a legacy directory, a dangling, absolute, or outside path, a symlink chain, a self-reference) is left untouched and never imported, and no commit metadata is invented for it. Previously such a request failed with `LINK_CONFLICT`. There is no new option, flag, wire field, or client change, so existing clients work unchanged, and ordered `afterLink` hooks, restart, and retention pinning behave as for any manual link, including a retry after a failed hook (`UNCHANGED`).
- Only symlinks are taken over. A regular file or directory at the name, a symlink whose record is automatic, version 1, malformed, or foreign, a manual link changed externally since it was recorded, and automatic link names still fail closed, and automatic reconciliation and startup never take a symlink over. The server re-checks that the symlink is unchanged (text, and inode where the storage reports one) and unrecorded immediately before the swap and fails closed otherwise. This is not a compare-and-swap, which the storage adapter does not offer, so do not edit a running server's storage root. A crash after the swap and before the record is repaired by repeating the same request.
- Case-insensitive volumes: a request for another spelling of a recorded link (`Latest` for a recorded `latest`, automatic or manual, including a link renamed in case outside the server) is one directory entry with an existing owner, so it fails with `LINK_CONFLICT` instead of replacing it and leaving two records. Before the swap the entry must be listed under exactly the requested spelling, and no protected name that differs only in case (a recorded link, a configured automatic link name even while its rule is dormant and has no record, or a managed artifact) may resolve to the same entry; it fails closed if the storage reports no inode identities while such a name exists. On a case-sensitive volume those names are distinct entries and stay independent.
- The `reset-storage` report note about remaining symlinks now says that an explicit link request replaces them while an automatic `--symlink` rule for that name still fails closed.

## 0.4.0

- Add the optional `afterLink` server hook (`ServerOptions.hooks`, and `--hooks <module>` modules) so a link change can be published. It runs after a managed link is durable, for an upload that moved an automatic link (after `afterCommit`, once per link that now points at the uploaded artifact, including an already-committed retry) and for an explicit `Client.link` / `swarm-deploy link` that passed every policy check. Its context is the secret-free, frozen `{ link: { name, target, mode, path, targetPath }, artifact, status, trigger }`, exported as `AfterLinkContext`, `HookLink`, `HookLinkMode`, `HookLinkStatus` and `HookLinkTrigger`.
- The client receives no success (`COMMITTED`, `ALREADY_COMMITTED`, `LINKED`, `UNCHANGED`) until the applicable `afterLink` calls return. A failing hook reaches the caller as the existing sanitized `HOOK_FAILED` code in the ordinary `FAILED` link result, upload final, or admission record, so clients and the wire format are unchanged, and `swarm-deploy link` now prints `HOOK_FAILED`. The caller sees that code only while it is still waiting: a client waits at most its idle timeout (60 s by default, 5 min at most) for the whole answer, which covers verification and commit, `afterCommit`, every `afterLink` call one after another, hooks queued ahead for the same link, and retention. If that expires first the client reports `UPLOAD_IDLE_TIMEOUT` instead, while the server still finishes its hooks. The durable link and artifact are never rolled back. Hooks must be idempotent on `link.name` plus `artifact.transferId`: repeating an unchanged link request (`UNCHANGED`) or retrying an upload re-runs the hook, so a failed publication can be retried without changing the link.
- A failed `afterLink` is observable server-side: `onFailure` gets the new `afterLink` `HookFailureContext.phase` (with `link`, and the link path as `path`) after the client was answered, a `failure` event and a `Link hook failed` warning are emitted, and a failed link request's `link` event carries the new optional `result` (`LINKED` or `UNCHANGED`) with `reason: 'HOOK_FAILED'`.
- Hooks run after the storage-root lease is released, so a slow hook never blocks commits, retention, recovery, or other links and cannot deadlock on the lease. The context is therefore a snapshot: a later decision may already have repointed the link, and retention may have removed an unpinned previous target. For one link name, hooks start in decision order and never overlap (an in-memory first-in, first-out line reserved under the lease; it does not survive a restart, and there is still no hook timeout). Hooks do not run for rejected or unauthorized link requests, for a manual link whose target is replaced, or for startup, scheduled, or retention reconciliation.
- **Fix.** After a `HOOK_FAILED` answer (any hook phase) the server now ends its write side and destroys the connection once the peer closes it, or after 5 seconds, instead of destroying it right behind the write. Over a real stream the immediate destroy could reset the connection before the client read the record, so the caller saw a connection reset instead of `HOOK_FAILED`. Other failure answers still close immediately and are unchanged.
- Configuring `afterLink` defers the post-commit retention pass until the hooks succeed, like `afterCommit`, so this commit's own link reconciliation runs before this commit's retention pass. That narrows, but does not remove, the chance that the link already moved: another commit's retention or reconciliation can do it first, and the hook then sees `UNCHANGED`. `status` is the link decision the call observed (`LINKED` when it created or repointed the link or repaired an automatic link's ownership record, `UNCHANGED` otherwise, including a manual ownership-metadata refresh for the same target), never proof of publication. Servers without `afterLink` are unchanged, including `afterCommit` ordering and its deferred retention.
- Add the runnable, **Node-only** `examples/link-publisher` hooks module and publisher (they use `node:child_process` and the global `process`, so they do not run on Bare; library hooks themselves work on Node and Bare). Each link change is passed as one JSON document on stdin to a script started without a shell: `SWARM_DEPLOY_PUBLISHER` names a JavaScript module file run with the current Node executable, not an arbitrary executable. Each call has a 20 s deadline: the publisher then gets `SIGTERM` and, 5 s later, `SIGKILL` (that direct child only), and the call always rejects with a timeout, even if the publisher exits zero after `SIGTERM`. It settles only once the child has exited, so an abandoned publisher cannot write over the next publication of the same link, and a call takes at most 25 s. The example's header shows how to size the client idle timeout for several sequential calls (25 s each).
- Add `swarm-deploy reset-storage --storage <dir> [--apply [--wait <ms>]]`. Without `--apply` it is a read-only preview of the
  private state under one storage root: commit records and how many have no
  payload, sessions, journals, staging, publications, the managed-link ledger,
  trash, lock residue, earlier archives, and the visible payloads and symlinks
  that would remain. With `--apply` it takes the storage lock, renames those
  directories and lock residue into
  `.swarm-deploy/archive/reset-<timestamp>-<random>/` with a `reset.json`
  marker, recreates them empty, and releases the lock. Nothing is copied or
  deleted; an archive is restored by moving it back.
- The reset never signals a process. A live lock holder makes `--apply` fail
  closed with exit `1`; `--wait` polls until the holder releases the lock, a
  holder whose PID is gone is retired automatically. Live and unreadable
  locks cannot be bypassed by a PID override.
- The report states what still blocks a true fresh start: remaining payloads
  keep their names (`FILE_EXISTS`) and remaining symlinks lose their ownership
  record (`LINK_CONFLICT`). `fresh start: yes` is printed only for a root with
  nothing visible left. Unsafe roots, symlinked internal paths, filesystem
  roots, and uninitialized roots are rejected with exit `2` before any change.
- Block server recovery after an interrupted reset until a reset retry
  completes, reject symlink ancestors, and refresh retained-file reporting
  after waiting for exclusive access.
- A retry after an interrupted reset, including a crash or power loss that
  skips error handling, resumes the archive the pending marker names instead of
  creating a second one. Progress is reconciled from what the archive holds,
  and a retry fails closed when the archive and the live directory both hold
  data or the named archive is gone. One reset always ends as one archive, so
  restoring it restores everything.
- Keep the archive marker bounded. `reset.json` is version 2: it names the
  metadata directories, summarizes lock residue as a count and a SHA-256 of the
  sorted names, and keeps the first attempt, the newest 16 attempts, and a total
  count with failure text clipped. A marker therefore stays readable after any
  number of stopped servers or retries, instead of becoming unreadable once its
  lock list outgrew the reader. Version 1 markers stay readable at the shared
  metadata size bound, a retry that resumes one first preserves it verbatim as
  `reset.v1.json`, and the preview counts lock residue rather than listing it.
- Document that `reset-storage` must run as the server's operating-system user:
  applying it as another user, such as `root`, leaves metadata the service
  cannot use. The command does not enforce this.
- Export `resolveLayout`, `inspectStorageLock`, and `isProcessAlive` from the
  storage layout module for the reset; existing lock behaviour is unchanged.

The deferred pass runs before `COMMITTED` or `ALREADY_COMMITTED`, so a slow retention pass can delay the reply. Servers without `afterCommit` rotate immediately as before.
- Run the deferred post-commit retention pass from an already-committed offer only for a transfer this process committed whose `afterCommit` has not yet succeeded. Other duplicate offers still invoke `afterCommit` but start no retention pass, so they cannot force repeated full scans. The owed-transfer set is in memory only and is cleared by server close.
- Reject a `--hooks` path whose extension is not exactly `.js`, `.mjs`, or `.cjs` before the module is loaded, so an unsupported extension gives a precise startup error instead of a runtime loader message.
- **Behavior change.** Give an authenticated transfer ID a single in-flight owner. A second connection offering a transfer another connection already owns is rejected with `FILE_BUSY` during the offer phase, so staging, commit, `beforeCommit`, and `afterCommit` never run concurrently for one transfer identity. Sequential retries, resumes, and verified reconnects are unaffected, but automation that uploads one artifact from several workers at once must now treat `FILE_BUSY` as "retry once the in-flight attempt finishes". The guard is per process, bounded by the connection limit, and released when the connection ends or the server closes.
- Release the transfer guard before awaiting `onFailure`, so a slow or hung failure callback cannot reject the client's legitimate retry. `onFailure` is observational and may therefore overlap the next attempt's lifecycle hooks; each connection still reports at most once, and the serialization of `beforeCommit`/`afterCommit` per transfer is unchanged.
- Bound the owed post-commit retention set at 1024 transfers, matching the connection ceiling, evicting the oldest owed transfer first. An evicted transfer keeps its committed artifact and leaves rotation to the next startup, scheduled, or commit-triggered pass.
- Reserve the derived fixed-series namespace: a captured `{series}` of exactly `fixed-` plus 64 lowercase hex characters never matches, so an uploaded filename cannot place itself in a version-only pattern's rotation group.
- Export `fixedSeriesKey` from the root API so operators can map a series in a commit sidecar or log line back to the template that produced it.
- Retrying a failed `afterCommit` normally takes the `ALREADY_COMMITTED` path, but there is no persistent hook-pending marker: any intervening retention pass (startup after a restart, scheduled or manual cleanup, or a concurrent commit's retention) can remove an out-of-window artifact first, and the retry is then a fresh upload.
- Write a resumable session at on-disk version 3 only when it carries a `sourceParent`, and at version 2 otherwise. Both are readable. A downgrade therefore loses the resumability of parent-bearing sessions only, instead of every session written by this version; draining in-flight uploads before a rollback still avoids it.
- Never rewrite the durable release identity of a commit record. Enabling or changing `artifactPatterns` while uploads are in flight makes a retry of already-committed bytes fail closed (`FILE_EXISTS` for a create-only name, a release-identity conflict for a replaceable name retried under the same transfer ID), so drain in-flight uploads before changing patterns.
- Commit-record compatibility is asserted only in the reading direction: records without release coordinates are read and excluded from count and version rotation. Whether older code tolerates records this version writes is untested.
- Document that a hung hook callback on a fresh or resumed upload also holds an active-upload slot and its staging reservation, so enough hung callbacks exhaust upload capacity until the server closes. Bounded timeout and anti-spam controls are tracked in issue #8.
- Document that an `offer`-phase `onFailure` context is built before the transfer ID is authenticated and is delivered even when that authentication failed, so its artifact fields must not be used as audit or idempotency keys.
- Document rollout, retry, path, and compatibility semantics.
